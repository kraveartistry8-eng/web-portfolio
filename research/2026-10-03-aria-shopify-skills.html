01

Executive summary

The table is a reasonable map of the 2026 role. Its tiering is sound: the core three are table stakes, the advanced three are what separate a theme editor from a developer, and the specialized three are where the new money is because almost nobody has them yet.

Two of its claims fail verification. The MCP row overstates what the documented endpoint does. The structured data row repeats a marketing position that controlled testing in 2026 contradicts. One more, the INP conversion claim, is the familiar pattern of a real metric carrying an unsourced business number.

The finding that matters most is not about the table at all. Before today, section 03 of your roadmap sold a Shopify Functions rebuild as the opening created by the Scripts shutdown, and no week in the plan taught Functions. That is now fixed in week 6. The same inconsistency still exists, unfixed, for measurement: the care plan promises a monthly page of numbers, and nothing in 27 weeks teaches you how to collect them after the checkout.liquid deprecation took the old method away.

The pattern worth naming

Both gaps are the same shape. The plan is strong on what you build and thin on what you measure and automate afterwards. That is the half a merchant pays monthly for, which makes it the expensive half to be missing.

02

The core three

Core · verified

Liquid, HTML, CSS, JavaScript

Accurate and uncontroversial. Liquid remains the template language for every non-headless storefront, and the June agentic work extended Liquid storefronts rather than replacing them.

Plan coverage: full. Weeks 2 to 5 are nothing but this. The product loops in week 3 are explicitly Liquid with CSS transitions and no library, which is the right constraint for learning it.

Core · verified, with a correction

Theme architecture, sections and blocks

Accurate, and the table's own wording lags. It says "2.0 Sections + Blocks" and "post-Horizons update". The current architecture is theme blocks, which Horizon introduced, and Horizon is the default theme for stores created in 2026. Dawn still uses the older section stacking and no longer receives new features.

Plan coverage: full, as of today. Weeks 1 to 5 were built on Dawn until this morning. They now start from Skeleton, which is both what theme init clones and what shopify.dev names as the recommended base.

Core · verified

GraphQL Admin and Storefront API

Accurate. The Admin API is how an app reads and writes store data; the Storefront API is how any headless or custom front end queries the catalogue. Both are GraphQL only for new work.

Plan coverage: partial. Week 15 writes GraphQL loaders against the Admin API inside the React Router app. The Storefront API is never touched, because the plan deliberately defers headless. That is a defensible trade, not an oversight.

Advanced · added to the plan today

Shopify Functions

Accurate. Functions customise Shopify's backend logic, compile to WebAssembly, and are written in Rust or JavaScript. Shopify recommends Rust for performance on large carts. The targets cover discounts, payment customisation, delivery options, cart and checkout validation, order routing, bundles, fulfilment constraints and pickup.

The sub-5ms figure comes from Shopify's own Scripts migration page, which describes Functions as executing in under five milliseconds against Scripts.

Plan coverage: none until today. Week 6 now writes a product discount Function in JavaScript and deploys it. JavaScript rather than Rust is the right first step: enough to be credible, far quicker to reach.

03

Where the table overstates

  1. Storefront MCP does not let an agent purchase, at least not at the documented endpoint

    The table says MCP "enables AI agents to browse, add to cart, and purchase autonomously." The documented UCP catalogue endpoint at /api/ucp/mcp exposes exactly three tools: search_catalog, lookup_catalog and get_product. shopify.dev describes it as catalogue only, with no cart or purchase capability, and every request must carry an agent profile URL.

    A separate, older endpoint at /api/mcp is reported to include cart management and ordering, and that one needs no authentication. [Low Confidence] on the second endpoint: secondary sources only, not confirmed against shopify.dev in this pass. The honest version of the claim is that the catalogue half is documented and real, and the transacting half needs checking before you say it to a merchant.

  2. Structured data probably does not do what the AIO row says

    The row claims JSON-LD "drives zero-click AI discovery and semantic search visibility." Controlled testing in February 2026 found that ChatGPT and Perplexity tokenise JSON-LD as raw text rather than parsing it semantically, and a multi-engine experiment across ChatGPT, Claude, Perplexity, Gemini and Google AI Mode found every system extracted visible HTML while hidden structured data was not processed at the point of citation selection.

    Against that sit vendor claims of 2.5x and 3.2x citation lift. None names a sample or a method. The balanced reading is that schema helps indirectly, through Google's own pipeline, and that what AI engines actually read is visible page content. The practical instruction inverts: write the answer on the page, do not hide it in a script tag.

  3. The INP conversion claim is the usual shape

    INP itself is solid. web.dev defines good as 200ms or under, needs improvement to 500ms, poor above 500ms, and names it the successor to First Input Delay. That page makes no claim about conversion or rankings.

    "Poor INP directly hurts conversion rates and search engine rankings" is a real metric carrying an unsourced business number. Core Web Vitals are a ranking input, and a weak one by Google's own description. Section 06 of your roadmap already forbids quoting numbers you cannot stand behind. This is one of them.

  4. "Framework-agnostic since June 2026" is premature

    Hydrogen's rebuild with Vercel is real: a complete rewrite, framework and runtime agnostic, decoupled from Remix and Oxygen, running on Next.js, Svelte, Nuxt or your own stack. But it was announced in that window, not shipped. It is in closed alpha, with public beta expected Q3 2026 and general availability Q1 2027.

    For you this is good news rather than bad. GA lands inside your plan window, every agency is re-skilling at the same time, and the target is Next.js plus the Shopify data layer rather than the old Remix-on-Oxygen stack.

04

The gap that is still open

Custom Pixels and server-side tracking is the one row in the table that your plan needs and does not have, and the reason is specific rather than general.

checkout.liquid was deprecated in two stages. Information, Shipping and Payment went on 13 August 2024, with automatic upgrades from 6 January 2025 that discarded those customisations. Thank you and Order status followed on 28 August 2025, which also covered script tags and additional scripts. Anything loading analytics through checkout.liquid, which for most stores meant Google Tag Manager, stopped collecting at those dates.

The Web Pixels API replaced it. Pixels now run in a sandbox, either as a standalone Custom Pixel written in the admin or inside an app, and they are subject to the customer privacy and consent layer rather than having free access to the page.

Why this is not optional for you

Your care plan is two promises. One shipped thing a month, and one page of numbers showing what it measured before and after. Section 03 calls that monthly page "the document that makes renewal a formality instead of a conversation."

That page needs event data from a checkout you no longer have raw access to. If a merchant's tracking broke in 2024 or 2025 and was never properly rebuilt, which is common, then your first month produces a page of numbers you cannot stand behind, or no page at all. The retainer is the business, and this is the skill the retainer runs on.

The correction is small in calendar terms. A Custom Pixel that fires the standard events into one destination is an afternoon, not a weekend. The judgement call is where it goes, because weeks 17 to 19 are already a three-weekend scope-build-deliver sprint and week 20 is titled Measure what the first job changed, which is precisely the week that currently assumes a capability you do not have.

Recommendation, not yet applied

Put a Custom Pixel into week 20, where the plan already intends to measure. One task: stand up a Custom Pixel on the dev store, fire the standard checkout events, and confirm they arrive. It replaces nothing, and it turns the care plan's second promise from an intention into a capability.

On the PII caveat

The table says Custom Pixels restore "PII data flow lost after checkout.liquid deprecation." That is loose. Shopify restricted that access deliberately, and pixels run sandboxed under the customer privacy and consent layer. What is restored is event data, and server-side forwarding is what makes it reliable. Sell the measurement, not the personal data.

06

Gaps in this research

  • The /api/mcp cart and checkout capability. Reported by several secondary sources, not confirmed on shopify.dev. Check before claiming an agent can transact on a store you built.
  • Whether Functions can make network calls. The functions documentation page does not address it. Matters if you ever scope a Function that needs outside data.
  • Insufficient data available for the general availability status of standard storefront events, and for Static Apps GA, both of which rest on single secondary sources.
  • Every conversion figure attached to any of these skills. No named study, no sample size, no method, in any source found. Treat the lot as unusable in a proposal.

What to do with this

Nothing today. Today is the partner account, the dev store, the CLI, Skeleton with hot reload confirmed both ways, and the brand with its one line.

Before week 6, nothing more. Functions is in the plan now and that was the urgent one, because you were selling it.

Before week 20, decide on the Custom Pixel. That week is called Measure what the first job changed, and it is the only week in the plan whose title describes something the curriculum cannot yet do.
