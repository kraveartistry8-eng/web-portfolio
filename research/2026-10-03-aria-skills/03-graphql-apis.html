Admin API and Storefront API

Two different APIs doing two different jobs.

The table treats them as one row. They are not interchangeable, and your plan touches one of them and deliberately skips the other.

01

What it actually is

The Admin API reads and writes a store's own data: products, orders, customers, metafields, discounts. It is what an embedded app talks to, and it is the API behind the loaders in your week 15 app. GraphQL is the only option for new work.

The Storefront API is the public, customer-facing read API for the catalogue and cart. It is what a headless front end queries, and it is what you would use if you built a store outside Liquid. It is also the layer the new agent tooling sits beside.

Both are versioned on a quarterly cadence, which means a build you ship is on a dated version and will need periodic attention. That maintenance obligation is itself a reason a merchant needs somebody on retainer, which is worth saying on a call.

02

Does the claim hold

Substantially, but "required for headless builds and catalog queries" describes the Storefront API and quietly mislabels the Admin API. The Admin API is required for every app you will ever build, headless or not, and it is the one your plan actually teaches.

03

The devil's advocate

  1. The quarterly version cadence is a liability you can sell

    Anything you build against these APIs ages on a schedule. Framed badly that is a defect in your work. Framed correctly it is the clearest possible answer to "what am I paying you for every month", and it is checkable rather than persuasive.

  2. Skipping the Storefront API is a real limit, not a neutral trade

    It is the right call for six months, because headless is deferred. But it means you cannot prototype anything outside Liquid, and the agent catalogue work sits adjacent to it. If an agency conversation goes technical, this is the most likely place to find the edge of what you have built.
